# Phase 2 M2 能带走的东西:device-side concat kernel

> 格式对齐 [phase2-m1-takeaway.md](phase2-m1-takeaway.md) 的端到端段:每条 = 一个带具体坑的认知 + 失效场景 + 为什么。
> M2 = Phase 2 首个真计算 kernel:gate_up 的 device 版 concat(N inputs / arbitrary axis / arbitrary rank,通用形式)。验证"device cat == torch.cat bit-exact"。三个消费者:① M6 loader GPU 化时 gate_up 在 device 上 cat(替代 Phase 1 的 CPU memcpy cat);② 通用形式本身是 kernel-writing 练手(N>2、任意 axis、任意 rank);③ 坐标映射算法是 M3 elementwise/reduction、M4 GEMM、M8 paged attention 的共同地基(idx→多维坐标反算 + 按轴切分 + 跨 input 定位)。

- **row-major 反算必须更新 rem(`idx %= dim`),不能复用 idx**:kernel 把 output 线性 idx 反算成多维坐标 `coord[i]`,循环里 `dim /= d_out_shape[i]; coord[i] = idx / dim` —— idx **没更新**则 coord[1] = idx/dim 含 coord[0] 的贡献,错。**失效场景**:shape `[2,3]` idx=5,期望 coord=(1,2);不更新 rem 算 coord[0]=5/3=1✓ 但 coord[1]=5/1=5✗(应 2,因 5=1×3+2)。**为什么**:row-major 下高维的 stride 大,低维坐标是"扣除高维贡献后的余数",不复用原 idx 就把高维贡献又算进低维。正确写法每轮 `rem %= stride` 让 rem 只剩当前维及以下的余量。这条是 M2 kernel 最核心的坑,也是所有"线性 idx → 多维坐标"kernel 的通病(M4 GEMM 的 tile 坐标、M8 paged 的 block table 索引都同源)。

- **output 字节偏移就是 `idx*dtype_size`,别用 coord 重推**:output row-major 连续,`idx` 已是线性索引,写入位置 = `(char*)out + idx*dtype_size`。**失效场景**:用 coord 循环累加 `out += coord[i]*dtype_size` —— 既漏乘 stride(coord 是坐标不是偏移)、又没必要(output 偏移 idx 直给)。**为什么**:coord 反算是为**定位 input**(沿 axis 扫描需要 coord[axis]),不是为算 output 偏移。把"反算 coord"和"算 out 偏移"混在一个循环里,会误以为 coord 也能算 out 偏移——但 output 不需要反算,idx 即偏移。区分清楚:coord 服务 input 定位,out 偏移服务 output 写入,两条独立路径。

- **input 字节偏移 = `Σ coord[d] × stride_d × dtype_size`,stride 从 input k 的 shape 推**:input k 的 shape = output shape 把 axis 维换成 `d_axis_sizes[k]`,其余维跟 output 同。**失效场景**:`input_ptr += coord[i]` 把 coord 当字节偏移直接加指针(char* 算术)—— 漏乘 stride(coord 是元素数非偏移)、漏乘 dtype_size(指针是字节单位)。**为什么**:coord 是多维坐标(元素计数),指针是字节地址,单位差两步(stride 把坐标转元素偏移,dtype_size 把元素偏移转字节偏移)。M2 的 stride 循环 `strides *= i==axis ? d_axis_sizes[k] : d_out_shape[i]` 是关键——axis 维用 input k 自己的轴长,其余维用 output 的(因 non-axis 各 input 相同)。倒序循环 + 先用 strides 再累乘,行内偏移算对。

- **CUDA device 代码禁 VLA(`coord[rank]` runtime rank 编不过)**:`std::int64_t coord[rank]` 里 rank 是 kernel 参数(运行时值),是变长数组(VLA)。**失效场景**:g++ 接受 VLA 作扩展(C99),但 **nvcc device 端每线程栈大小固定,不允许 VLA**——编不过或生成错误代码。**为什么**:VLA 要运行时栈帧调整,device 栈是静态分配的固定大小,没有这个机制。改 `coord[MAX_RANK]` 固定大小 + 编排层(concat.cpp)查 `rank > MAX_RANK` 抛错。MAX_RANK=10 覆盖所有合理张量,上界检查在 host 层做(不在 kernel 内做,kernel 不抛异常)。这条是 CUDA 跟 host C++ 的隐藏差异:g++ 放过的扩展 nvcc 不放。

- **kernel 只看 device 内存,`std::vector<Tensor>` 是 host 对象进不了 kernel**:concat 的 inputs 是 `vector<const Tensor*>`,但 kernel 不能收 vector(host 对象,活在 CPU 栈)。**失效场景**:把 vector 直接传 kernel → 编不过(host STL 容器无 device 语义)或语义错。**为什么**:kernel 跑在 GPU,只能读 GPU 上的内存;vector 的 data() 指向 host 内存,kernel 解引用它得到垃圾。正确拍平:concat.cpp 在 host 攒三个数组(`ptrs[]`/`axis_sizes[]`/`out_shape[]`),逐个 `cuda_memcpy_h2d` 到 GPU,kernel 收 `void**`(GPU 指针数组)+ `const int64_t*`(GPU 数组)+ 标量。**N 个指针本身也得在 GPU 上**——kernel 读 `d_ptrs[k]` 是间接层(d_ptrs 在 GPU,它指向的 input 数据也在 GPU),两层都要在 device。这条是"host 容器喂 kernel"的通用模式,M3/M4 凡 kernel 要 N 个输入或元数据数组都同构。

- **Tensor move-only 撞 `vector<Tensor>` 墙,Phase 2 第一个 N-Tensor op 才暴露**:Phase 1 所有 op 收单 `const Tensor&`(rmsnorm/matmul/attention 的 Q/K/V),pybind11 `cast<Tensor&>()` 取引用不拷贝,绕开 move-only。concat 收 N 个 Tensor(`vector<Tensor>`),pybind11 造临时 vector 要**逐个拷贝** Tensor → 撞 `Tensor(const Tensor&)=delete`(Phase 1 防双释放的 move-only 设计)。**失效场景**:直绑 `m.def("concat", &concat)` → build 报 `use of deleted function 'Tensor::Tensor(const Tensor&)'`,报错栈 `new_allocator.h:191` placement new copy。**为什么**:pybind11 转 Python list→vector 时构造临时 vector,元素要拷贝构造;by const-ref 也救不了(仍要构造临时 vector)。解法:签名改 `vector<const Tensor*>`(非持有观察,跟 Phase 1 的 `const Tensor*` bias/mask 惯用法同源,从"1 个可选"推广到"N 个必选"),binding 加 `concat_py` 遍历 `py::list` 用 `cast<const Tensor&>()` 取引用再 `&t` 攒指针——**全程不拷贝 Tensor**,绕开 move-only 墙。concat_py 存在的理由跟 attention_py 同:签名有 pybind11 不直绑的类型。torch 的 `vector<torch::Tensor>` 没此问题(torch::Tensor 可拷贝,共享 storage 引用计数),这是裸指针 Tensor 设计的直接后果非 pybind11 锅。

- **`cudaMalloc` 2MB 分配粒度 vs no_leak 测试(我误诊了 3 次,最终探针钉死)**:no_leak 测试循环 100 轮 to_cuda+concat,to_cpu,记 cuda_free_bytes 前后,期望 delta≈0。实测 delta=2,097,152(2MB)恒定。**我三次误诊**:① 猜"进程第一次 CUDA 调用初始化 context 预留 2MB"——但整文件跑时测试 1-6 早初始化过,free0 已是稳态基线,推翻;② 猜"测试 1-6 的残留 GPU 对象"——但 delta 方向是 free1<free0(少了),残留释放该让 free 升非降,推翻;③ 猜"逐轮泄漏 bug 6"——但 bug 6(三个临时 buffer 40B/轮)100 轮该泄漏 4KB 非 2MB,量级差 500 倍,推翻。**最终 per-iter 探针钉死**:delta 从第 1 轮就 2MB,10/100/200 轮恒定不变(不累积)→ 不是泄漏;`del cpp_cuda`(最后一个活的结果 Tensor,8KB)释放整个 2MB → 是 **cudaMalloc driver 2MB 段粒度**:即使申请 8KB,driver 按 2MB 段记账,只要进程内还持有任何 cudaMalloc 块,该段不算 free;循环里 rebinding 旧块释放新块分配但**总有一个活的**,占一个 2MB 段 → free_bytes 恒定少 2MB。**失效场景**:no_leak 测试把"循环里始终持有活对象"误当"泄漏"。**为什么 + 修法**:no_leak 测的是"临时内存每轮回收",不该被"结果 Tensor 持有"干扰。修法 = 循环内 `del x1_cuda, x2_cuda, cpp_cuda, cpp_cpu, cpp`(每轮强制 GPU 零活对象),任何未回收的临时 buffer 都表现为 delta 累积可见——这是 M1 no_leak 精神(循环 N 轮看累积)的正确延续。M1 没此问题是 M1 循环里 Tensor 构造后立即析构无跨轮持有,M2 concat 结果天然持有到轮末。**M7 pool 后此现象失效**:pool 用大块 cudaMalloc 切分,小分配走 pool 内部 free-list,cudaMemGetInfo 不再随小 alloc/free 波动(pool 持大块不还)→ 那时 no_leak 改测 pool 内部 free-list 长度。跟 [[feedback-industrial-claims-verify]] 同源——这次又是我抓我自己的误诊,且 3 次全错才探针。

- **concat.cpp 三个临时 buffer 必须 free(launch 后 sync 完再 free)**:d_ptrs/d_axis_sizes/d_out_shape 三个 GPU buffer 是 concat.cpp 攒的元数据,launch 后要 `cuda_free`。**失效场景**:return 前不 free → 每次调 concat 泄漏这三块(no_leak 测试该红)。**为什么 + 联动**:kernel launch 是 async,concat.cpp launch 后若立即 free 三个 buffer,kernel 可能还没读完 → use-after-free/race。正确顺序:**launch → `cudaGetLastError()`(抓 launch 配置错)→ `cudaDeviceSynchronize()`(等 kernel 完 + 抓执行错)→ free 三个 buffer → return**。sync 是"先确保 kernel 读完元数据,再释放元数据"的前提。M2 correctness-first 全程同步,async(overlap 下一 op)是 Phase 5 concern,gated on stream 抽象。

- **`cudaGetLastError()` + `cudaDeviceSynchronize()` 两段式,不只 sync**:concat_launch launch 后只 sync 不够。**失效场景**:launch 配置非法(grid=0、block 过大)时错误是"粘性"的,靠 `cudaGetLastError` 取;只靠 sync 不保证能浮出 launch 失败(kernel 根本没起,没执行错可 sync 抓)。**为什么**:launch-time 错(配置)和 run-time 错(执行)是两类,分别用两个 API 抓。两段式:`CHECK_CUDA(cudaGetLastError())` 抓 launch 错(不等),`CHECK_CUDA(cudaDeviceSynchronize())` 抓执行错 + 等 kernel 完。这是 CUDA 错误处理的教科书两段式,M4 GEMM/M8 paged 的 launch wrapper 都该照此。

- **`vector<const Tensor*>` 非持有语义,跟 Phase 1 `const Tensor*` bias/mask 同源**:concat 对 inputs 是非持有观察(只读 shape/data,不存),接口本就该收"一组 Tensor 的观察引用"非"一组 Tensor 的值。**失效场景**:收 `vector<Tensor>`(值语义)→ 撞 move-only + 语义错(concat 不该拥有 inputs)。**为什么**:Phase 1 的 `const Tensor*` bias/mask(linear/attention)就是"非持有可选参",concat 把它从"1 个可选"推广到"N 个必选",访问语法 `inputs[i]->` 跟 `bias->` 一致。move-only 对象的 N 元观察容器,裸指针是标准做法(C++ 性能库惯用法)。reference_wrapper 也行(不可 null 更安全)但访问语法 `inputs[i].get().` 啰嗦,concat 内部已到处 `inputs[i]->data()`,裸指针更自然。

## 共性

Phase 2 M2 教的不是"写个 concat",是"把 row-major 坐标映射 + host/device 数据拍平 + move-only 接口约束三件一次性钉死"——坐标反算更新 rem 是所有 idx→多维 kernel 的通病(M4/M8 同源)、host 容器喂 kernel 的拍平模式是 N 元输入 kernel 的通用骨架、move-only 撞 vector 是裸指针 Tensor 设计在 N 元 op 的必然代价。CPU 前向(Phase 1 loader 的 gate_up CPU memcpy cat)作 bit-trusted oracle 一字不动,M2 是纯增量 GPU op——单变量隔离(CUDA concat 错 vs CPU oracle 对)的对拍地基,torch.cat 作独立 CPU 参考(非 op 的 CPU 路径,这 op 没有 CPU 路径)。反向探针(关 memcpy → 7 测试红 → 还原绿)证明 green 是真拷贝非碰巧,M5/M8 ablation 纪律的 kernel 版。
